# LunchCare Corporate — White‑label платформа корпоративного здорового питания

**Бизнес-модель:** B2B2C  
**Роль:** White‑label SaaS для сервисов доставки здоровой еды и кейтерингов, которые выходят на корпоративный рынок.

---

## Практическое задание №1 – Elevator Pitch и Lean Canvas

### Elevator Pitch (лифтовая речь)

> «Сотрудники хотят питаться правильно, но в офисе часто нет здоровых вариантов, а заказывать индивидуально — дорого и неудобно. HR‑отделы тратят десятки часов в месяц на сбор заказов и контроль оплат.
>
> **LunchCare Corporate** — white‑label платформа для сервисов доставки здорового питания и кейтерингов. Партнёры запускают под своим брендом готовое решение: компании получают единый кабинет для управления подписками сотрудников, а сотрудники — доступ к сбалансированным рационам с доставкой в офис или домой.
>
> Партнёр увеличивает оборот за счёт стабильных корпоративных заказов, а компании — повышают вовлечённость и снижают больничные.»

### Lean Canvas (9 блоков)

| № | Блок | Содержание |
|---|------|-------------|

| 3 | **Уникальное ценностное предложение** | • **Для партнёра:** white‑платформа под своим брендом + автоматизация B2B-продаж (счета, акты, отчёты), быстрый выход на корпоративный рынок.<br>• **Для HR:** единый кабинет для управления подписками, контроль бюджета, автоматическая отчётность.<br>• **Для сотрудников:** доступ к здоровым рационам с доставкой, удобный каталог с фильтрацией по КБЖУ и аллергенам. |

| 6 | **Потоки доходов** | • SaaS‑подписка от партнёра (фикс за активных корпоративных клиентов или % от оборота).<br>• White‑Label лицензия (единоразово за настройку и брендирование).<br>• Комиссия с транзакции (1–3% от объёма заказов).<br>• Расширенные модули (интеграция с 1С, премиум‑аналитика). |
| 7 | **Структура издержек** | • Разработка и поддержка платформы (frontend, backend).<br>• Техподдержка и аккаунт‑менеджмент для партнёров.<br>• Хостинг, CDN, хранение данных.<br>• B2B‑маркетинг и продажи.<br>• Юридическое сопровождение (договоры, соответствие нормам общепита). |

### 3. MVP и MLP

**MVP (первая версия – «скелет»)**

| Кто | Что входит в MVP |
|-----|------------------|
| Сотрудник | Регистрация по email-домену компании, просмотр меню на сегодня/завтра, разовый заказ или подписка на неделю. |
| HR | Импорт сотрудников через CSV, задание лимитов каждому, сводка по расходам (простая таблица). |
| Партнёр | White‑label (логотип + свой домен), получение агрегированных заказов (CSV) каждое утро, админка для загрузки меню. |
| Система | Проверка лимита при заказе, автоматическая агрегация заказов в 9 утра, отправка партнёру. |

**MLP (вторая версия – «чтобы пользователи полюбили продукт»)**

- Push/Telegram-уведомления о доставке еды в офис.
- Гибкие группы сотрудников (по отделам, проектам) с разными бюджетами.
- Красивые дашборды для HR с графиками расходов.
- Автоматическая генерация закрывающих документов (акты, счета).
- Расширенный каталог: фильтры по КБЖУ, аллергенам, диетам (вегетарианское, без глютена, keto).
- Интеграция с корпоративными календарями (Google/Outlook) для напоминаний «закажите обед».

### 4. Детальные требования для двух главных историй из MVP

#### US2 – Просмотр меню с КБЖУ и аллергенами

**Функциональные требования (ФТ)**

1. На главном экране после входа отображается переключатель дат (сегодня/завтра/календарь на 7 дней вперёд). По умолчанию выбрано сегодня.
2. Каждая позиция меню содержит: название, описание, фото (опционально), калорийность (ккал), белки/жиры/углеводы, список аллергенов, цену.
3. Пользователь может добавить позицию в корзину одним кликом. Корзина отображается как иконка с бейджем количества товаров.
4. При нажатии на позицию открывается детальная карточка с полным составом и увеличенным фото.
5. Доступна фильтрация: «без аллергена X», диапазон калорий, тип блюда (суп, салат, горячее).
6. Если на выбранную дату меню ещё не загружено партнёром, показывается понятная заглушка «Меню появится после 18:00».

**Нефункциональные требования (НФТ)**

1. Загрузка страницы меню (до 50 позиций) и применение фильтров занимают не более 1 секунды (95-й перцентиль).
2. Интерфейс должен быть адаптивным: одинаково удобно на десктопе (1920px), планшете (768px) и мобильном телефоне (375px).
3. Все изображения блюд оптимизированы: lazy loading, формат WebP, размер не более 200 КБ.
4. Доступность для людей с ограничениями: контрастность текста 4.5:1, поддержка скринридеров (WCAG 2.1 AA).
5. Доступность платформы в рабочие часы (с 8:00 до 20:00 по местному времени) – 99.9%.

#### US9 – Агрегация заказов и отправка партнёру

**Функциональные требования (ФТ)**

1. Система автоматически в 9:00 каждый день (время настраивается партнёром) собирает все заказы сотрудников на предстоящую дату (обычно завтра).
2. Формирует единый CSV-файл со структурой: дата доставки, название компании, подразделение (если есть), название блюда, количество порций, особые пожелания.
3. Отправляет файл партнёру через заранее настроенный API-эндпоинт. При ошибке отправки – повторяет 3 раза с интервалами 5, 10, 20 минут.
4. Если API не настроен, система отправляет файл на резервный email партнёра.
5. В админке партнёра есть кнопка «Сформировать отчёт вручную» для любой даты (полезно для отладки).
6. Система логирует каждую отправку: время, статус (успех/ошибка), количество заказов в отчёте.
7. Защита от дублей: для одной даты отчёт формируется и отправляется только один раз (повторная отправка только по запросу партнёра).

**Нефункциональные требования (НФТ)**

1. Формирование отчёта для 500 сотрудников (примерно 300 заказов) должно занимать не более 3 секунд.
2. API-вызов отправки имеет timeout 10 секунд. Если партнёр не ответил за это время – считается ошибкой, идёт retry.
3. Все логи агрегации и отправки хранятся не менее 30 дней (для аудита и разбора инцидентов).
4. Партнёр может изменить время ежедневной агрегации через интерфейс настроек (новое время вступает в силу на следующий день).
5. Сгенерированный CSV-файл должен содержать итоговую строку (total) с общим количеством порций и общей суммой для удобства партнёра.

## Практическое задание №3 – DDD, BDD, Wireframes, API

### 1. Доменные зоны (DDD)

Выделено 5 ограниченных контекстов.

#### 📁 Домен 1: Управление клиентами (Client Management)

**Что делает:**  
Регистрация компаний (корпоративных клиентов) и их сотрудников, управление ролями (HR, сотрудник), верификация через корп. почту.

**Глоссарий:**
- **Корпоративный клиент (Company)** – компания, заключившая договор с партнёром.
- **HR-администратор (HR Admin)** – сотрудник компании, который управляет группами и лимитами.
- **Сотрудник (Employee)** – конечный потребитель, которому доступен заказ.
- **Корпоративная верификация (Email Domain)** – подтверждение через домен компании (example.com).

---

#### 📁 Домен 2: Меню и каталог (Menu & Catalog)

**Что делает:**  
Управление блюдами, рационами, расписанием меню на дни, хранение состава, КБЖУ, аллергенов.

**Глоссарий:**
- **Позиция меню (Menu Item)** – конкретное блюдо со всеми характеристиками.
- **Рацион (Meal Plan)** – набор блюд на приём пищи (обед, завтрак).
- **Дневное меню (Daily Menu)** – список доступных позиций на конкретную дату.
- **Аллерген (Allergen)** – вещество, которое может вызвать реакцию (молоко, орехи).

---

#### 📁 Домен 3: Заказы и агрегация (Orders & Aggregation)

**Что делает:**  
Приём заказов от сотрудников, проверка лимитов, группировка заказов по компаниям и датам, формирование сводок для партнёра.

**Глоссарий:**
- **Заказ (Order)** – выбор одного или нескольких блюд на определённую дату.
- **Подписка (Subscription)** – автоматическое повторение заказа (например, каждый понедельник).
- **Агрегированный отчёт (Aggregated Report)** – файл со всеми заказами компании на дату.
- **Лимит (Budget Limit)** – максимальная сумма или количество порций, доступная сотруднику (или отделу).

---

#### 📁 Домен 4: White‑Label и партнёрское управление (Partner & White‑Label)

**Что делает:**  
Брендирование, управление аккаунтами партнёров, настройка времени агрегации, интеграция с внешними учётными системами.

**Глоссарий:**
- **Партнёр (Partner)** – сервис доставки, использующий платформу.
- **Брендинг (Branding)** – логотип, цвета, поддомен/домен.
- **Настройки отправки (Dispatch Settings)** – время агрегации, способ (email/API).
- **Счёт (Invoice)** – документ для оплаты компании (генерируется в этом домене или внешней системой).

---

#### 📁 Домен 5: Отчёты и аналитика (Reports & Analytics)

**Что делает:**  
Формирование отчётов для HR (расходы по сотрудникам/отделам) и для партнёра (популярность блюд, отмены).

**Глоссарий:**
- **HR-отчёт (HR Report)** – таблица с ФИО, датами заказов, суммой, остатком лимита.
- **Популярность блюда (Item Popularity)** – количество заказов позиции за период.
- **Отмена (Cancellation)** – заказ, который сотрудник отменил до дедлайна.

### 2. BDD: Критический путь MVP

Критический путь – **сотрудник заказывает обед с использованием корпоративного лимита**.

#### 🟢 Успешный сценарий

**Дано:**  
- Сотрудник Анна зарегистрирована в платформе (корпоративная почта @company.ru).
- Её HR задал лимит 5000 ₽ на месяц.
- Партнёр «ЗОЖ-Еда» загрузил меню на завтра.

**Когда:**  
Анна заходит на сайт, выбирает завтрашнюю дату, добавляет в корзину «Овощной салат» (250 ₽) и «Куриный суп» (300 ₽), нажимает «Оформить заказ».

**Тогда:**  
- Система проверяет лимит (остаток 5000 – 550 = 4450 ₽) и подтверждает заказ.
- Анна видит сообщение «Заказ на завтра подтверждён».
- В её истории появляется запись о заказе.
- Система запоминает заказ для утренней агрегации.

---

#### 🔴 Сценарий отказа (превышение лимита)

**Дано:**  
- Тот же Анна, но лимит уже израсходован (остаток 200 ₽).
- Она пытается заказать «Стейк из лосося» (600 ₽).

**Когда:**  
Анна нажимает «Оформить заказ».

**Тогда:**  
- Система вычисляет, что сумма заказа превышает лимит.
- Анна видит красное сообщение: «Недостаточно средств на корпоративном счёте. Остаток 200 ₽. Свяжитесь с HR или выберите другие блюда».
- Заказ не создаётся, корзина остаётся неизменной.
- HR не получает уведомление (но может посмотреть отчёт позже).

### Ручка 2 — Создание заказа

**Запрос:** `POST /api/v1/orders`

**Тело запроса:**
```json
{
  "employee_id": 123,
  "delivery_date": "2026-05-12",
  "items": [
    { "menu_item_id": 101, "quantity": 1 },
    { "menu_item_id": 102, "quantity": 1 }
  ]
}

Ответ (201 Created):
```json
{
  "order_id": 5001,
  "employee_id": 123,
  "delivery_date": "2026-05-12",
  "status": "confirmed",
  "total_amount": 550,
  "remaining_budget": 4450,
  "message": "Заказ успешно оформлен"
}

Ошибка (дублирование заказа):
```json
{
  "error": {
    "code": "DUPLICATE_ORDER",
    "message": "Вы уже сделали заказ на эту дату"
  }
}
